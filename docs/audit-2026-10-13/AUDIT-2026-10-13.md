## 2. 🔴 P0 级（数据/结果错误，建议最优先）

### P0-1 列识别顺序缺陷：低置信推断列抢占高置信明确列的槽位
**（对 Net/Gross/L/W/H 标准英文装箱单必错）**

**复现**（探针 `probes/cls-audit-probe5.js`，对象：项目自带 `test-packing-list.xlsx`）：
- 表头 `Item | Description | Net | Gross | L | W | H | VoL | PackageType | Remark`（国际装箱单标准格式，行业模板通行）
- 实际解析结果：**`"Final": 8.774 × 10.8 × 2.12m`**——即 Net 列当"长"、Gross 列当"宽"、H 列当"高"；真实尺寸列 L/W 被整列丢弃；"型号"= Remark 列值（Final/Estimated）；重量全 0。
- UI 侧后果：推荐直接失败（"货物 'Final' 尺寸 8.77×10.80×2.12m 超过门约束"），计算按钮禁用，用户拿到的是一个**彻底错误的单子**。

**根因（三处叠加，`field-parser.js`）**：
1. `FIELD_KEYWORDS`（L52-106）缺 **"Net"/"Gross"** 单词（只有 "Net Weight"/"Gross Weight"）→ Net/Gross 列落入样本推断；
2. `classifyColumn` 的宽松兜底（L233-240）：**任何**列数≥3、全整数、值域 1~5万 的列都会被判为 `possibleDimension`(low)——"Net"8774 等命中；
3. `extractItems` 按列序先到先得（L675-680）：Net(第3列) 先占 `lengthCol`、Gross(第4列) 占 `widthCol`，之后 **high 置信的 L/W 列（第5/6列）因"槽位已占"被直接跳过**。→ 低置信列战胜高置信列。

**次要根因**：`Remark` 无排除规则，其值 "Final"/"Estimated" 符合 model 正则（L214-221）→ 被判为 model(medium)；`Description` 虽被识别为 description(high)，但 `extractItems` 不使用 description 字段，导致真实货物名丢弃。

**影响**：生产环境的英文装箱单（行业最常见写法之一）默认解析全错；错误通过警告通道仅给出"低置信提示"，不阻断，用户极易直接采用错误数据计算。

**修复方向**：
- `extractItems` 改两阶段：先处理 high 置信列（length/width/height/grossWeight/…），`possible*` 类 low 置信列只填充剩余空槽；
- `FIELD_KEYWORDS` 补 `Net`/`Gross` 单词（整头精确匹配已支持）；
- `possibleDimension` 兜底逻辑加前置条件：**不存在**任何明确尺寸列时才启用；
- `extractItems` 增加 `description → model` 回退；列识别增加 remark/备注 → unknown 排除。

### P0-2 相邻完全相同的数据行被静默删除

**复现**（探针 `probes/cls-audit-probe3.js` 3a/3a2）：
- 输入 3 行（两行完全相同、带表头）：`BOX-A×10 / BOX-A×10 / BOX-B×5`
- 解析结果：**总件数 15（应 25）**——第二行同数据行被删除。
- 对照组：带序号列 → 不删除（因行内容不全等）；多 Sheet 合并对照组正常。

**根因**：`field-parser.js` `cleanMergedRows()`（L599-616）为"多 Sheet 合并时去掉重复表头"设计，实现为**相邻行 JSON 全等即删**，误伤真实数据行（同规格分两行录入的装箱单常见）。

**修复方向**：去重仅针对"与表头行相同的行"（如：命中 ≥2 个 FIELD_KEYWORDS 的行且与前一个表头相同），或按 Sheet 边界逐 sheet 处理表头重复后直接拼接，不再做全量相邻去重。补一条回归：无序号列 + 两行相同数据 → 全保留。

## 3. 🟠 P1 级（业务误导 / 功能死锁）

### P1-1 混合推荐给出物理不可行的方案（单件超载货物）

**复现**（探针 2/4 + UI 实测 `cls-e2e-smoke2.py` 场景 C）：
- 输入：1 件 30,000kg、2×2×2m 的普通尺寸重货
- `autoRecommend` → **"混合方案：20尺普柜×2"**（`container-db.js` `recommendMixedContainers`）——**物理不可行**：单件 30t 超过 20GP 载重 28.2t，每个 20GP 都装不下这"1 件"，更谈不上分装。
- UI 完整链路：推荐区显示"已自动推荐混合装箱方案：20尺普柜×2"→ 用户点计算 → 结果 **"所需箱数 0 个 | 推荐2箱…实际 EMS 算法优化为 0 箱 | 1 件未能装入"**（图：`cls-e2e-C2-result.png`）。
- 同时：真正可行的 40FR（39.6t 口径下）在整条推荐链上**完全不出现**——用户得不到任何"换 40FR"的提示。

**根因**：
- `classifyItemByContainerType` 不做重量检查 → 30t 件被归入 "标准货"；
- `recommendMixedContainers` 的 `pickBestSingleSpec`/`calcUnitsForGroup`（container-db.js L656-749）只做几何检查 + 按总重除箱，**没有"单件重量 ≤ 单箱 payload"过滤**（对比：planner.js 的 `filterContainerTypes` 有重量过滤，所以计算路径反而能把 30t 装进 40FR——推荐层与计算层口径不一致）。

**修复方向**：推荐层所有候选箱型过滤加 `单件重量 ≤ payload` 硬条件；对"单件 > 所有标准箱 payload"的情况给出显式提示（推荐重载箱型/拆货），不要产出"×N 箱"伪方案。

### P1-2 "推荐失败"场景计算按钮死锁（无法计算）

**复现**（UI 实测 `cls-e2e-smoke2.py` 场景 A2，用真实测试单）：
1. 上传任一"推荐失败"的单子（含超限货等）→ 推荐面板显示"自动推荐失败，请手动选择箱型"，计算按钮**禁用**；
2. 勾选"启用混合装箱"→ 状态被重置（`useMixed:false`）、按钮仍禁用——**死循环**（勾选触发 `refreshContainerRecommendation()` → 依旧失败 → `renderFailedRecommendation` 把状态重置回来）；
3. 手动点选任一箱型（40HQ）→ state 已设置成功（`containerSpec` 有值）但**按钮仍禁用**——`bindManualContainerButtons`（app.js L1306-1355）设置状态后**未调用 `ensureCalculateButton()`**，按钮的 disabled 属性无人刷新。

**结果**：推荐失败场景下用户**完全无法进入计算**（三条路径全被堵死）。这是当前最容易撞到的死胡同（任何有超限货的单子都会进去）。

**修复方向**：
- `bindManualContainerButtons` 点击回调末尾调用 `ensureCalculateButton()`（一行）；
- "启用混合"的 change 分支去掉"重刷推荐→被重置"的闭环：勾选即显示面板等待用户选箱型（或让 failed 渲染函数不再强制重置 `useMixed`）。

### P1-3 FR 柜载重口径与官方数据源冲突，"修正"推理有误

**事实对照（Exa：Hapag-Lloyd 官方规格）**：

| 箱型 | 代码当前值 | Hapag 官方 | 备注 |
|---|---|---|---|
| 20FR payload | **27,500kg**（注释称"修正"） | **31,260kg**（34,000 gross − 2,740 tare） | 原值 31,260 即为官方值 |
| 40FR payload | **39,600kg**（注释称"修正"） | **44,050kg**（50,000 gross − 5,950 tare） | 原值 44,050 即为官方值 |

**推理错误**（container-db.js L75-76/L91-93 注释）：
- "原 31260 超过 20' 最大总重 30480（数学不可能）"——FR 柜不受 ISO 668 标准柜总重限制，Hapag 官方文档明确"up to 45,000 kg for Flatracks"（20FR 34t / 40FR 50t 各批次更高）；
- "原 44050 隐含自重仅 950kg"——**算术错误**：50,000−44,050 = **5,950kg**（恰为 Hapag tare），不是 950（把 45t 假设当成了官方总重）。

**实测影响**（探针 1/7/8）：
- 28,000~31,260kg 单件货：20FR 拒装（按官方可装）；
- 40,000~44,050kg 单件货：40FR 拒装（按官方可装）；
- 结果被推到更大/更贵方案，或直接"推荐失败"（30t 以上场景叠加 P1-1）。

**修复方向（需爹地拍板口径）**：改回官方值（31,260 / 44,050）或保留现有保守值但**更正注释推理**；如取保守值，建议在 UI 中对"单件重量落在保守差额区间"的货物给提示（实际可否装取决于承运人批次）。

---

### P1-4 "无重量列将使用体积估算重量"承诺未实现（载重校验静默失效）

**事实**（field-parser.js L701 与 L857-859）：
- 警告文案："未找到重量列，**将使用体积估算重量**"；
- 实际行为：`weight = 0`——**没有任何体积估算实现**。探针 3b：`[{C1, weight:0}, {C2, weight:0}]`。

**影响**：无重量列的装箱单会长驱直入：所有载重约束（单件/累计/承重比）静默失效，结果页面**不会**报超重，用户可能拿到严重超重的装载方案照做。

**修复方向**：二选一（需爹地拍板）——① 实现体积估算（需定密度口径，如 300kg/m³ 可调）；② 保守方案：文案改为"未找到重量列：所有货物按 0kg 计算，**载重校验不会生效**，请补充重量列后重新上传"，并将该警告升级为醒目级别。

### P1-5 推荐与装载一致性缺口：超长货"分类可装、实际装不进"

**复现**（探针 9a）：
- 13m 长货（单维 > 40FR 超长上限 11.652+0.5=12.152m）：`classifyItemByContainerType` 返回 **'FR'（可装）**，实际装载 unplaced（装不进）。
- 区间：单维长度 ∈ (12.152, ∞) 的货类均如此（12.3m 实测同样"分类 FR → 算不出"）。

**根因**：`checkFRLengthRule`（container-db.js L336-351）只检查"超过内长的维度个数"，不看**超长幅度**是否在 `FR_REALITY_LIMITS.maxOverLengthTotal` 之内；超长分支直接返回 'FR'。

**影响**：用户按推荐准备 FR 方案，计算时才发现装不下；且结果页未明示"超出超长预算"（只有泛化的"未装入"）。

**修复方向**：classify 的超长分支增加 `max(dims) ≤ L + maxOverLengthTotal` 校验，超出即 'none' + 明确原因文案（"超出 40FR 超长上限，需特种平板/特种审批"）。

## 4. 🟡 P2 级（口径确认 / 改进建议）

1. **默认允许 6 向翻转过于激进**（依赖翻转的推荐需要明示）：2.6m 高货被推荐 20GP（需横放装载）、3.5m 宽货被推荐 OT（需竖放装载）——实测均几何成立，但设备类货物行业默认"不可倒置/侧放"。建议：默认口径与爹地确认；UI 在"依赖翻转才能装"时给出显式提示。（探针 9/10）
2. **45HQ 未纳入单件分类**：`classifyItemByContainerType` 的"超长优先 FR"规则（L388）对 11.653~13.5m 货物直接判 FR，**忽略 45HQ（内长 13.556m）**——正确解析演示中 11.98m 桥架被推 "40FR"，实际引擎用 45HQ 装下了（且 45HQ 更常规、更经济）。建议重审"超长优先 FR"旧规则。（探针 6）
3. **重心约束缺失**：行业（CTU Code 60/50：60% 重量应位于长度中间 50% 区间、重心偏差 ≤ ±5% 箱长）为通行红线；当前文档已声明不做。且启发式评分（dblScore）有"里端集中"倾向，加重偏差风险。建议列入后续里程碑（或输出"重心位置估算"提示）。（Exa：CTU Code）
4. **成本模型缺失**：推荐以"箱数最少/利用率"为目标——“45HQ×8 优于 20GP×20”类结论未计入 45HQ 溢价与内陆限制；“尾组合并”可能把普货并入更贵的特种柜。建议后续引入箱型成本权重。
5. **推荐提升文案 bug**（app.js L1641-1661）：先 `recommendation.primary = promoted` 再在文案中引用 `recommendation.primary.code`——"优于原推荐"显示的是**新箱型自己**（如"20FR 优于原推荐 20FR"），且对比箱数也查的新箱型。
6. **skippedContainers 原因文案固定错误**：统一写"剩余货物的尺寸/门约束不符合此箱型"，但 30t 案例的真实原因是**重量**（超载被拒）——用户会被引向错误方向。（packing-engine.js L1520-1528）
7. **结果页晦涩文案**：推荐 2 箱 vs 实际 0 箱时显示"推荐2箱…实际 EMS 算法仅需 0 箱即可装完所有货物"——"0 箱"无意义且自相矛盾。（app.js L1892-1894）
8. **数据小项**：20GP payload 28,200 vs Hapag 官网 28,130（差 70kg，建议注释口径）；20OT 门宽 2.338 vs Hapag 2.344、20OT payload 28,100 vs 一批次 30,200（保守值，确认即可）；`structured-fr` 排序含 KT-800 等硬编码魔法数字（注释已说明来源，维护风险留意）。
9. **性能/维护备注**：`getEffectiveMaxDims` 在放置热路径每空间×每朝向重复调用（常量结果，可提出循环）；`detectOverlaps` 大规模分支 `items.indexOf` 为 O(n)。
