## 1. P0 硬伤

### P0-1 `Planner.planContainerAssignment` 无限循环 → 内存耗尽（OOM）

**现象**：混合装箱模式下，只要订单里有一件"名义高度 > 分配箱内高、但允许旋转后装入"的货物，`planContainerAssignment` 就陷入死循环，每轮把一个**空箱** push 进 `assignments`，内存线性增长直到 OOM。浏览器/WebView 表现为页面先卡死、再崩溃。

**证据**（`docs/review-evidence-2026-10-13/probe9.js`）：

```
$ node --max-old-space-size=64 probe9.js repro
最小复现：单件 0.5×0.5×2.5（20GP 内高 2.393，可旋转装入 → 分类 20GP）
  分类=20GP（Planner 用 0.01 容差）
  调用 planner.planContainerAssignment …
FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript out of memory

$ node probe9.js control        # 同一件货物高度改成 2.3（< 20GP 内高）
  分类=20GP
  assignments=1 unassigned=0
  分配详情=[{"c":"20GP","n":1,"reason":"可叠货聚合，1件"}]
```

真实数据同样命中：仓库自带 `test-packing-list.xlsx` 的解析结果中含一件 `1.38×2.02×2.5`，`probe9.js parsed` 明确标出它满足触发条件：

```
1.38×2.02×2.5 (7.0m³) 分类=20GP 可用=20GP/40HQ/40GP/45HQ/20OT/40OT/20FR/40FR ← 触发无限循环条件（建组箱=20GP 内高2.393 地板13.9）
```

**位置**：`planner.js`
- 建组条件（只查体积）：`:192` `if (usableCodes.has(c.code) && itemVol <= c.L * c.W * c.H * VOLUME_FACTOR)`
- 加入前检查（查体积/重量/底面积/高度）：`:228-231`，其中 `:231` 为 `nextHeight > stackableGroup.container.H`
- 失败分支（push + 回退索引重试）：`:232-239`，`:238` 为 `i--; // 重试当前 item`

**根因**：建组门槛与加入门槛**不同口径**。`:192` 只看体积（≤0.85×箱容），而 `:228-231` 还看底面积与高度。当某件货物体积合格但 `item.h > 建组箱内高`（货物可旋转放倒，故分类为 20GP/40HQ）时：新建组 → 加入检查失败 → push 空组 + `i--` → 用**完全相同**的输入重新建同一个组 → 必然再次失败 → 无限循环，且每轮泄漏一个 `assignments` 元素。

> 注意：`classifyItemByContainerType` 允许 6 方向旋转，而 Planner 的高度预检用的是**未旋转的 `item.h`**，两者口径不一致是触发本 bug 的直接条件。20GP 内高 2.393m / 40HQ 2.7m，意味着**任何 2.4m 以上、可放倒的货物**（立式机柜、长杆件、高板件…）在混合模式下都会踩中。

**影响面**：仅"混合装箱"路径（`calculate → options.mixedContainers` 非空）。但混合装箱是 20GP/40HQ 摆不开时的主推功能（Step 3 勾选项默认提供），且 `Planner` 是 `calculate` 混合分支的第一步，失败即整单算不出。

**修复建议**（按优先级）：
1. **建组条件与加入条件同口径**：`:192` 建组时同时校验 `itemFloor <= c.L*c.W`、`item.h <= c.H`（或按 6 朝向的**最小高度**校验，与分类器口径一致）。
2. **禁止无条件 `i--` 重试**：把"回退重试"改为**有失败计数的重试**（同一 item 连续失败 2 次即 `unassigned.push(item)` 并 `continue`），或在进入分支前打"已重试"标记。
3. **兜底熔断**：循环加硬上限（如 `stackableItems.length * 3` 次迭代）后强制退出并把余量打入 `unassigned`。同类 `i--` 重试模式在 `:238/:280/:311` 三处存在，需一并加护栏。
4. **回归测试**（当前 17 个套件无一覆盖）：新建 `test-regressions-c1.js`，断言"单件 0.5×0.5×2.5 + 混合箱型"能在 1s 内返回且 `unassigned` 有明确记录；再补一条"新建组必能接纳首件"的不变量断言。

### P0-2 重量缺失时静默置 0kg → 载重约束永久失效

**现象**：装箱单没有可识别的重量列时，解析器发出警告"未找到重量列，**将使用体积估算重量**"，但实际实现直接把 `weight` 置 0。0kg 货物在装载与自检中**永远不会触发**任何载重检查：`packSingleContainer` 的重量闸门（`packing-engine.js:525`）与 `selfCheck` 的超重报错（`:1707`）都只是 `currentWeight + weight > payload`，0 恒不成立。

**证据**：
- 代码：`field-parser.js:701`（警告文案） vs `field-parser.js:857-858`（`} else if (isNaN(weight)) { weight = 0; // 无重量时设为0`）
- 实测：`probe7.log`（真实 `test-packing-list.xlsx`）解析出的 14 条货物 **全部 0kg**；`probe2.log` D 段显示 0 重量的 272 件订单"正常"给出 4 箱方案，`hasErrors=false`。

**影响**：这是最危险的一类缺陷——**静默失效**。用户看到的是"解析成功 + 方案生成 + 无报错"，但方案里没有载重约束：超重货会被判为可装，港口/堆场按此装箱会触发超重。对以"装箱可行解"为交付物的工具而言，这属于必须堵死的口子。

**修复建议**：
1. 半成品禁令：`weight === 0` 的货物**不得进入计算**（`validateCalculationInput` 增加重量 >0 校验），UI 在 Step 3 明确标红"缺重量"，引导用户在列映射里指定重量列或手工补录。
2. 若确要保留自动估算，就**真的实现**：按 `体积 × 密度`（如按 `PackageType` 或品类给默认密度）估算并在结果里标注"估算重量"；同时让警告文案与实际行为一致。
3. `selfCheck` 增加一条 `zeroWeight` 警告：箱内零重量货物数量 >0 时输出告警。

### P0-3 相邻完全相同的数据行被静默删除 → 件数凭空缩水

**现象**：`FieldParser` 与 `app.js` 各自有一处"相邻行完全相同则合并"的去重（本意是处理 Excel 合并单元格产生的重复行）。当装箱单里出现**逐字相同的相邻行**（同型号同尺寸同数量的多行，或没有可区分 ID 列时），后面的行被**直接删除而非数量累加**，件数静默少算。

**证据（`docs/review-evidence-2026-10-13/probe12.log` A 段）**：构造 35 行数据，其中后 10 行与第 1 行逐字相同（`Item|Description|Qty|Gross|L(mm)|W(mm)|H(mm)`）：

```
原始行=36 → app.js 去重后=27（差 9 行）
FieldParser 解析：数据行=26 条目数=26 总件数=26      ← 10 行相同数据只留 1 条，9 件消失
```

即**10 件货只算成 1 件**。注意 `sheets.data` 里 36 行原始数据是完整的，是"提条目"这一步丢的。

**位置**：
- `field-parser.js:601-607`（`// 简单的去重：如果相邻两行完全相同，合并` → `if (JSON.stringify(prev) !== JSON.stringify(curr))`）
- `app.js:617-624`（`processFileBuffer` 里同样的整行 JSON 比对，注释写明"matching FieldParser behavior"）

**影响**：件数/重量/体积全线偏小 → 方案"装得下"但实际漏发。这是**静默**错误（无告警、无提示），且与"按整行 JSON 相等"的判据强相关：只要 ID 列被忽略（见 P1-5 的 `Remark`/`Description` 错列乱象）或客户单里本就重复，就会命中。

**修复建议**：
1. 去重只在**行内存在"合并单元格痕迹"时**生效：例如仅当 ID 列为空、或该行有 `null/''` 的空列（合并单元格的典型特征）才合并；
2. 若确属重复行，**语义应为"数量累加"而不是"删除"**（把这两行视同一条 + `quantity += 1`）；
3. 至少要在 Step 2 给出可见提示："检测到 N 行重复数据，已合并/累加，请确认"，把静默变显式。

## 2. P1 重要问题

### P1-1 20FR/40FR 载重口径与 Hapag-Lloyd 官方规格矛盾（偏保守 2.6–4.5t）

| 箱型 | 代码值 | 行业值 | 来源级别 | 判定 |
|---|---|---|---|---|
| 20FR | **27,500 kg** | HL：最大总重 34,000 / 自重 2,740 / **载重 31,260**；DSV：30,140；莲花柜厂：30,400 | R1（HL 官方规格 PDF） | 代码**偏低 2.6–3.8t** |
| 40FR | **39,600 kg** | HL：最大总重 50,000 / 自重 5,950 / **载重 44,050**（另有 55,000/60,000 重载版本）；DSV：40,000 | R1 | 代码**偏低 0.4–4.5t** |

**位置**：`container-db.js:71-103`（`:77` = 27,500，`:94` = 39,600）。代码注释给出的修改理由是"20' 最大总重 30,480kg（ISO 668）数学不可能"与"40FR 按 45t 总重口径运营"。而 GL 官方规格明确 **平板柜不适用普柜的 30,480kg 总重口径**：20' 平板柜给到 34,000kg，40' 平板柜给到 50,000–60,000kg（HL《Container Specification》《THINK BIG》）。也就是说，**被"修正"掉的旧值 31,260 / 44,050 恰是 HL 官方值**，本次"修正"建立在错误前提上。

**影响**：单件或整箱毛重落在 27.5–31.3t（20FR）/ 39.6–44.05t（40FR）区间时，系统会判"超载/不可装"，用户被迫拆单或改箱型——直接多花钱、多开箱。

**修复建议**：以单一来源（HL 官方规格）重建 FR 载重并注明"承运人口径可调"；或在箱型库中区分"普柜 ISO 总重口径"与"平板柜强化总重口径"，把取值写进注释（含来源链接与级别）。

### P1-2 默认 5cm 容差吞掉一整列/层 → 箱数上浮

有效排布长度 = 箱内尺寸 **减一个 5cm 容差**（`container-db.js:150-154`，`packing-engine.js:871-877`）。当货物尺寸是箱内尺寸的"整倍差一点"时，这 5cm 会直接吃掉一整列/一层。

**实测（`docs/review-evidence-2026-10-13/probe6-B.log`，40HQ，默认容差 0.05）**：

| 立方尺寸 | 理论格排上限 | 扣 5cm 后格排 | 实测装入 | 达成率 |
|---|---|---|---|---|
| 0.4m | 900 | 870 | 870 | 96.7% |
| 0.5m | **480** | **460** | **460** | 95.8% |
| 0.6m | 240 | 228 | 228 | 95.0% |
| 0.75m | 144 | 135 | 135 | 93.8% |
| 0.8m | 90 | 84 | 84 | 93.3% |

**端到端箱数影响（`probe11.log`，1440 件 0.5m 立方 @40HQ，同一条命令、只改容差）**：

```
tolerance=0.05: 箱数=4 每箱=460+460+460+60 平均利用率=58.9%
tolerance=0.04: 箱数=4 每箱=460+460+460+60 平均利用率=58.9%
tolerance=0.03: 箱数=3 每箱=480+480+480    平均利用率=78.5%
tolerance=0.01: 箱数=3 每箱=480+480+480    平均利用率=78.5%
```

即默认参数下 **多付整整 1 个 40HQ 的海运费**，且第 4 箱只装 60 件（利用率极低的"尾箱"）。

**根因**：5cm 容差被当作"排布长度的一次性硬扣减"，而 0.5m 货物铺满 40HQ 内长需要 12.000m ≤ 12.032m（真实余量 3.2cm）——余量小于容差，于是最后一列被整列放弃。

**修复建议**：a) 容差按"总长只影响最后一件/两端分摊"处理，而不是整体扣减；b) 或默认容差降到 1–2cm（实测 0.01–0.03 均能保住整列）；c) 在结果页显示"因操作间隙损失的最后一列/层"提示，让用户自行决定是否收紧容差。

### P1-3 `tolerance: 0` 被静默改写为 0.05

**位置**：`packing-engine.js:887` `const tolerance = options.tolerance || 0.05;` —— `0 || 0.05` 结果为 0.05，用户显式设置的"零间隙"被吞。注意 `calculate()` 本身（`:2177` 用 `== null` 判断）是正确的，但下游 `packSingleContainer` 把 0 又改了回去。

**实测（`probe4.log` B 段）**：

```
0.5m 立方 480 件 @40HQ：
  tolerance=(未传): 装入=460/480
  tolerance=0    : 装入=460/480   ← 0 被当成 0.05
  tolerance=0.001: 装入=480/480
  tolerance=0.01 : 装入=480/480
  tolerance=0.03 : 装入=480/480
  tolerance=0.04 : 装入=460/480
calculate(tolerance=0)   480 件：箱数=2（首箱 460 + 次箱 21）
calculate(tolerance=0.01) 480 件：箱数=1
```

UI 上容差输入框 `min=0`（`app.js:1100-1110`），用户完全可能设为 0 —— 结果箱数从 1 变 2。

**修复建议**：统一改为 `options.tolerance == null ? 0.05 : Number(options.tolerance)`，并在全库清查 `|| 默认值` 形式的数值型参数（`packing-engine.js` 与 `container-db.js` 均有多处）。

### P1-4 空间充足却漏装（"地面被占满 + 承重启发式"组合）

**实测（`probe4.log` A 段 / `probe6-A.log`）**：20GP 装 60 件 0.4m 小件（20kg）+ 1 件 1.2×1.2×1.0 不可叠大件（500kg）：

| 情形 | 结果 |
|---|---|
| 默认（`smart` 排序，大件排最后） | **装入 60/61，大件未装**，箱容利用率仅 **11.6%** |
| 大件排首位（`input-order` / `weight-desc`） | **61/61，1 箱装满**（15.9%） |
| 换 40HQ | 61/61（余量够，地面还留 1.2m 通道） |
| 小件自重加到 200kg | 仍装不下（不是"承重不足"单一原因） |

**根因链**（逐条实测）：
1. `smart` 三级分组把"轻型不可叠"排在最后（`packing-engine.js:2009-2025`，tier 3）；
2. 小件先把地面铺满（此处铺到 x≤5.60/y≤2.00，剩余地面仅 0.25×0.302m），大件在 z=0 已无整块地面；
3. 转向"放在小件上方"时被承重启发式拦下：`checkWeightBearing`（`:440-479`）要求下方接触重量的**折算和** ≥ 上方重量×0.5（`SUPPORT_WEIGHT_RATIO`）。1.2×1.2 底面上铺 9 件 0.4m 小件时，折算和就等于这 9 件自重（20kg 档 = 20kg；实测把单件加重到 200kg 也仅 200kg）< 500×0.5 = 250kg → 两档实测**都拒绝**；
4. 上方空间本身是够的（`mergeSpaces` 在 4 行满格时能合成 `5.6×1.6×1.94` 整块，探针 `probe5b-A.log` 已证），所以瓶颈在**排序 + 承重启发式的组合**，而非几何。

**影响**：单次装箱路径（`mixedMultiContainerPack` 兜底、`mergeTailContainers` 重装、Planner 组内）都会吃到这种"地板被小件占满 → 大件无处安放"的漏装，表现为利用率虚低、箱数虚高。默认单箱型路径因多起点优化（`multiContainerPack` 会试 5 种策略 + 随机洗牌）**有时能救回**（该例端到端 `calculate` 恰好命中了好顺序，1 箱装完），但这是"运气 + 时间预算"，不是保证。

**修复建议**：a) 候选策略集补入 `weight-desc` 与大件优先（现候选列表 `:1304-1310` 恰好缺这两个）；b) 对"未装件"做一次**重排重试 pass**（先把未装大件放首位再装一遍，装净即采纳——与 `mergeTailContainers` 的"全量装净"判据复用）；c) 承重启发式增加"地面/上层可替代"判断：某件在 z=0 无位置时才用承重闸门，避免"宁可空箱也不放"。

### P1-5 常见装箱单表头（`Net`/`Gross`）识别失败，自带样例解析错乱

**实测（`probe7.log`，输入 = 仓库自带 `test-packing-list.xlsx`）**：

```
列映射：["Item→id","Description→description","Net→possibleDimension","Gross→possibleDimension",
        "L→length","W→width","H→height","VoL→volume","PackageType→unknown","Remark→model"]
解析告警：[…"列3（表头"Net"）无尺寸关键词，但数值范围疑似尺寸列，已推断为尺寸（请确认）",
          "未找到数量列，默认每行数量=1","未找到重量列，将使用体积估算重量",…]
解析结果（首条）：Final | 8.774×10.8×2.12 | qty=1 | 0kg
```

后果三连：① 重量列被抢去当尺寸 → 尺寸跨列混拼出 8.774×10.8×2.12m 的"货物"；② 真实的 `Net/Gross`（8774/10800kg）弃用，重量全 0（叠加 P0-2）；③ 型号列落到 `Remark` 上，SKU 名变成 `Final`/`Estimated`。

**第二组证据（`probe12.log` A 段，构造标准英文单 `Item|Description|Qty|Gross|L(mm)|W(mm)|H(mm)`，真实尺寸 1200×800×600mm）**：

```
列映射=["Item→id","Description→description","Qty→quantity","Gross→possibleDimension","L(mm)→length","W(mm)→width","H(mm)→height"]
解析尺寸=["0.1×0.8×0.6", …]      ← 长度被 Gross(100) 污染：1.2m → 0.1m（差 12 倍）
```

即**正确映射的 `L(mm)` 列被嗅探出来的 `possibleDimension` 列覆盖**：同一条货物长度从 1.2m 变成 0.1m（体积偏小 12 倍）→ 计算会给出"远小于实际仍装得下"的方案。这比"尺寸偏大"更危险：偏大会被门/尺寸约束拦下，偏小会一路放到结果页。

**位置**：`field-parser.js` `FIELD_KEYWORDS`（`:52-106`，`grossWeight` 有 `Gross Weight` 但**无裸 `Gross`**，`netWeight` 有 `Net Weight/NW` 但**无裸 `Net`**）；数值嗅探改名 `possibleDimension` 的分支 `:231/239/256/262`。

**影响**：主流程第一环即失真。UI 的 Step 2 提供了列映射修正与"请确认"警告，所以**可人工救回**——但默认结果是不可用的，且"重量全 0"没有任何显式阻断（见 P0-2）。真实客户装箱单里 `Net/Gross` 是最高频的表头。

**修复建议**：a) 关键词表补 `Net`、`Gross`、`N.W.`、`G.W.`、`净重`、`毛重`（精确匹配优先于数值嗅探）；b) 尺寸列的数值嗅探加**互斥约束**：同一行已被判为尺寸的列不再参与重量候选，反之亦然；c) 型号列缺失时按 `id + description` 兜底，`Remark/备注` 列入忽略词；d) 解析质量门：重量全 0 或尺寸 > 箱内尺寸上限时，Step 2 直接阻断确认（不给"下一步"）。

### P1-6 箱型库无皮重（tare）→ 无法输出总重/VGM，也没有最大总重口径校核

`CONTAINER_DB`（`container-db.js:6-104`）只有 `payload`，没有 `tare`/`maxGross`。后果：
- 结果页与 PDF 只报"载重利用率"（相对 payload），**没有整箱总重（货重+皮重）**，也说不出 VGM；
- 校核口径停在"货重 ≤ payload"，缺少"总重 ≤ 最大总重"这一层。

**行业依据**（R1）：SOLAS VI/2（2016-07-01 生效）要求每个实箱在装船前提供 **VGM（验证总重）**，且"集装箱不得装至超过安全合格牌标明的最大总重"（IMO MSC.1/Circ.1475；英国 MCA MGN 534；Maritime NZ 同）。

**修复建议**：箱型库增补 `tare`（HL/DSV 规格可查）与 `maxGross`；结果页与 PDF 增加"整箱总重 / VGM 提示"卡片，并加一条自检：`货重 + tare > maxGross` → 报错。

### P1-9 推荐层给出**物理不可行**方案（单件 30t → "20GP×2"）

**实测（`probe12.log` B 段）**：单件 3.0×2.0×1.5m / 30,000kg：

```
recommendContainer      → needsMixed: 总重30000kg超出单箱载重，需多箱装载
autoRecommend           → type=mixed … 已自动推荐混合方案：20尺普柜×2
recommendMixedContainers→ 20尺普柜×2
calculate(20GP)         → 装入=0/1 未装=1 hasErrors=true（unplaced）
calculate(40HQ)         → 装入=0/1 未装=1 hasErrors=true（unplaced）
```

推荐层说"20 尺普柜×2"，而同一件货在 20GP 上实测 0 件可装；且这是**单件**，物理上不可拆分到两个箱子。

**根因链**：
1. `recommendContainer` 的单件超重闸门用的是**全箱型最大载重**（`container-db.js:457`，`Math.max(...CONTAINER_LIST.map(c => c.payload))` = 40FR 的 39,600），30t 因此"不算超重"；
2. 落入 20GP 分支后，`totalWeight > gp20.payload` → 逐级比较 40HQ/45HQ 载重 → 都不满足 → 返回 `needsMixed`（`container-db.js:585-596`）；
3. `recommendMixedContainers` 的 `calcUnitsForGroup` 只看**总量**：`ceil(30000 / 28200) = 2`（`container-db.js:687-689`），完全没有"单件不可拆"的概念；
4. 于是向用户展示一个既不可行、也无法被后续计算兑现的方案（计算会给出 `hasErrors=true` + 未装 1 件）。

**影响**：推荐面板是用户第一个相信的东西（"推荐 20GP×2"），与计算结论直接冲突；业务上会误导报价与订舱。

**修复建议**：`calcUnitsForGroup`/`recommendMixedContainers` 增加**单件级可行性闸门**：任一单件的重量 > 候选箱 payload，或尺寸不满足该箱门/尺寸约束 → 该箱型直接出局，并在推荐文案里明确说"单件 XXX（30,000kg）超出全部普柜载重，需特种箱（FR 39,600kg 级）或拆件"，而不是给一个装不下的箱数。
